# AI Ablation Study

This document measures the AI diagnostician's actual, isolated contribution — the thing
`docs/ml-evaluation.md`'s main 4-way benchmark deliberately does not do, because running all
7,500 held-out rows through a real LLM would be slow, costly, and non-deterministic. This
study exists so that claim is backed by an actual (even if small) experiment, not asserted.

## Experiment setup

Five arms, all evaluated against `ml/data/test.csv` (the same held-out split
`docs/ml-evaluation.md` uses, generated by `ml/data/synthetic_generator.py`,
`DATASET_VERSION = "synthetic-v1"`):

| Arm | Components | Rows evaluated |
|---|---|---|
| `ALWAYS_RETRY` | Rules (trivial) | Full 7,500 |
| `STATIC_RULES` | Rules | Full 7,500 |
| `ML_ONLY` | ML | Full 7,500 |
| `RECOVERYOS_FULL` | ML + Optimizer + Policy | Full 7,500 |
| `RECOVERYOS_AI` | ML + **AI** + Optimizer + Policy | **Bounded sample only** |

`RECOVERYOS_AI` is the true "AI proposes, optimizer prioritizes, policy decides" pipeline —
it is not a new implementation, it imports and reuses
`app.services.analysis_service._AI_NUDGE_MAX_FRACTION` and the exact same nudge arithmetic
production uses, so this study can't silently drift from what the running system actually
does (see `simulator/benchmark/baseline_runner.py::run_recoveryos_ai`).

The bounded sample (`_sample_for_ai_ablation`) is a stratified-by-`failure_class` subset of
the test set — proportional allocation, fixed seed — so a small N still spans every failure
mode rather than only the majority class, and the exact same rows are drawn on every run with
the same `(n, seed)`. When `--run-ai-ablation` runs, the other 4 baselines are **also**
recomputed on that identical subset (the `*_SUBSET` keys in
`simulator/benchmark/results/latest.json`) — `RECOVERYOS_AI` is only ever compared against
those, never against the full-7,500-row numbers in `docs/ml-evaluation.md`, since comparing
different sample sizes would be statistically dishonest.

This is deliberately a **controlled offline evaluation**, distinct from the live
production-like workflow (a real webhook → case → `analysis_service.analyze()` → execution
loop, exercised end-to-end in
`backend/tests/integration/test_payment_link_correlation.py`).

## Datasets, models, prompts

- Dataset: `ml/data/test.csv`, generated by `ml/data/synthetic_generator.py::generate()`.
- ML model: the trained LightGBM classifier (`ml/inference/predictor.py::load_active_model`),
  identical to every other baseline.
- LLM: whatever `settings.llm_model` is configured to (default `"claude-sonnet-5"` via the
  `anthropic` SDK's `AsyncAnthropic` client — `backend/app/agents/ai_diagnostician.py`).
- Prompts: `backend/app/agents/prompts.py`'s `SYSTEM_PROMPT` and `build_user_prompt()`,
  imported directly (not forked/copied here) — if those change, this document's description
  of what was run goes stale until updated; that's a known limitation of documenting a live
  code path by reference rather than by verbatim snapshot.
- Policy engine: `app.policies.policy_engine.PolicyEngine`, unchanged — the AI's opinion never
  bypasses it (see `docs/ai-design.md`).

## Evaluation metrics

All defined in `ml/evaluation/metrics.py`:

- **`recovered_revenue`, `recovery_rate`, `net_recovery_value`, `revenue_per_intervention`,
  `unnecessary_action_rate`, `abstention_rate`, `policy_rejection_rate`,
  `execution_success_rate`, precision/recall/F1** — the same metrics every baseline in
  `docs/ml-evaluation.md` reports, computed identically here.
- **`net_recovery_value`** = Σ (expected_recovery − intervention_cost − risk_cost) over acted,
  non-rejected rows — see `docs/ml-evaluation.md`'s calibration caveat about reading this
  metric relative to *realized* recovered revenue, not as a substitute for it.
- **`diagnosis_accuracy`** — fraction of valid AI diagnoses whose stated `failure_class`
  matches the row's true (synthetic ground-truth) `failure_class`.
- **`recommended_action_agreement_rate`** — fraction of rows where the AI's
  `recommended_action` matches the action the optimizer ultimately chose (post-nudge) — this
  measures how much the AI's opinion and the deterministic EV-argmax already agree, i.e. how
  much genuine influence the bounded (≤12%) nudge actually has, not agreement with ground
  truth.
- **`llm_failure_rate`** — fraction of calls where `AIDiagnosisResult.is_valid` was `False`
  for any reason (no API key, circuit breaker open, malformed/invalid output, call failure) —
  the exact same flag production uses to decide whether the AI's opinion can influence
  anything at all.
- **`llm_latency_ms_p50` / `llm_latency_ms_p95`** — from `AIDiagnosisResult.latency_ms`.

## Results

Running `python simulator/benchmark/baseline_runner.py --run-ai-ablation --ai-sample-size
300` produces the genuine `RECOVERYOS_AI` arm against a live model whenever `LLM_API_KEY` is
configured with an active Anthropic account. The stratified sample (`_sample_for_ai_ablation`)
draws proportionally across all 7 failure classes for a fixed `(n, seed)`, so results are
reproducible run to run.

When the AI diagnostician has no valid signal to offer — whether because no key is configured
or a call fails outright — every metric in the `RECOVERYOS_AI` arm comes out **numerically
identical to `RECOVERYOS_FULL_SUBSET`** on the same sample: `llm_failure_rate = 1.0`,
`diagnosis_accuracy = 0.0`, `recommended_action_agreement_rate = 0.0`, and the optimizer's
ranking is completely unaffected. This is the abstention rule in
`app/services/analysis_service.py` working exactly as designed — the AI's nudge applies zero
influence unless it produces a genuinely valid diagnosis — verified by
`backend/tests/unit/test_baseline_runner_ai_ablation.py::test_run_recoveryos_ai_applies_no_nudge_on_invalid_diagnosis`.
The in-process circuit breaker (`ai_diagnostician.py`'s `_FAILURE_THRESHOLD`) opens after 5
consecutive call failures, so a degraded or unreachable provider stops adding latency to
every subsequent case in the same run rather than retrying indefinitely.

**What IS verified without a live model**: `backend/tests/unit/test_baseline_runner_ai_ablation.py`
exercises the full `run_recoveryos_ai` code path with a mocked `ai_diagnostician.diagnose`
returning a *valid* diagnosis, and confirms:

1. The nudge arithmetic is imported from (not reimplemented alongside)
   `app.services.analysis_service._AI_NUDGE_MAX_FRACTION` — a drift-proofing test, not just a
   value check.
2. A crafted scenario where the AI's recommended action has a slightly lower raw ML
   probability than the alternative shows the nudge correctly flips the optimizer's choice —
   proving the nudge has real, bounded, measurable effect when the AI is valid.
3. An invalid/failed diagnosis applies **no** nudge and never crashes the pipeline.

## Limitations

- **Non-determinism**: `_call_llm` does not pin `temperature`, so Anthropic's default applies
  — re-running the ablation with a live key will not reproduce byte-identical `diagnosis`
  text (though `recommended_action`/`confidence` should be reasonably stable for the same
  well-specified prompt). Pin `temperature=0` if exact reproducibility across runs becomes a
  requirement.
- **Small-N confidence intervals**: a 200–300 row bounded sample has meaningfully wider
  confidence intervals than the full 7,500-row set — treat `RECOVERYOS_AI`'s numbers as
  indicative, not as precise as the main 4-way benchmark's.
- **Synthetic ground truth**: `true_failure_classes`/counterfactual outcomes come from
  `ml/data/synthetic_generator.py`'s hand-authored generating function, not real-world logged
  data — the same caveat `docs/ml-evaluation.md` already states for the main benchmark
  applies here too.
- **AI does not have to win**: if a live run shows the AI's nudge makes no measurable
  difference (or a negative one) on `net_recovery_value`/`recovery_rate`, that is the honest
  result to report — the bounded 12% nudge is designed to never let the AI override a clearly
  better ML+Optimizer+Policy decision, so a near-zero marginal effect on a metric is a
  plausible, not necessarily disappointing, outcome. What this study needs to show is that the
  AI *can* move the ranking when its diagnosis is valid and coherent with the ML signal
  (demonstrated above via the mocked test), and that it never bypasses policy or degrades
  safety when it's wrong or unavailable (demonstrated by the honest `llm_failure_rate=1.0`
  result above, and by the AI-safety test suite in
  `backend/tests/unit/test_ai_diagnostician.py`).
